## Recommendation

Use Streamlit Community Cloud for a controlled testing pilot, based on
`feature/multiyear-plants-and-tiered-sla`, after a small reliability patch. The
application is already written in Streamlit; a UI rewrite or separate hosting
backend is unnecessary for an initial test. Start with the committed 2025 data,
hourly snapshots and one simulated year. Test fixed-capacity dispatch first,
then capacity sizing separately. Correct the financial accounting before using
the reported returns to compare investments.

The six-tab UI renders in headless checks and a real 8,760-hour dispatch solve
completed optimally. Default 40-week capacity sizing also completed optimally.
Neither demonstrates that a public deployment will stay inside shared hosting
resources under concurrent use.

## What the tool does

1. Selects one wind and one solar DUID's historical generation shape, a NEM
   regional spot-price series, and an offtaker load profile. Custom CSVs can
   substitute generation, prices and absolute load.
2. Builds a stylised PyPSA network for generation, PV-connected battery storage,
   delivery, merchant sales, optional purchases, allowed shortfall and penalties.
3. Uses HiGHS through Linopy to optimise dispatch. Optional investment sizing
   chooses renewable, battery and connection capacities, charging annualised
   investment and operating costs and valuing contracted and merchant energy.
4. Replays historical inputs into operating years with degradation and price
   escalation. It then calculates delivery statistics, dispatch plots, financial
   comparisons, project finance, sensitivities and CSV/XLSX exports.

Important interpretation:

- This is a deterministic portfolio model with perfect foresight over the input
  period. It is not a forward NEM forecast, a network-constrained NEM dispatch
  model, or stochastic underwriting.
- Matching is evaluated from interval dispatch, while contractual delivery
  allowances/floors aggregate energy over annual, monthly or daily periods.
  “90% delivery” does not mean 90% renewable matching in every interval.
- Purchased power counts towards fulfilled delivery; renewable matching and
  contractual delivery should be presented separately.
- Batteries charge from the PV bus. Current link directions prevent charging
  from wind or market purchases. See `ppa/network.py:232–245,270–282`.
- Capacity sizing is off by default. Hard minimum delivery is a separate,
  opt-in sizing constraint; defaults can rationally accept penalties.
- Load profiles are stylised or reference profiles unless the user uploads real
  data. Selecting a historic DUID supplies a shape, not a bankable new-build yield.

| High | Finance adapter sums MW samples without snapshot duration for merchant sales, purchases and total generation. These volumes are 2×/4×/12× too high at 30/15/5 minutes. PPA and penalty MWh come from correctly integrated summaries, making the components inconsistent. | `ppa/financial_model.py:236–248,279–288` |
| High | Battery discharge is included as new generation, counting stored energy a second time. This affects generation-based LCOE and post-PPA merchant-volume assumptions. The plant picker year slider is misleading, rather than a proven startup crash:
with `[2025]`, its default is `(2021, 2025)`. Pinned Streamlit 1.57 expands the
bounds to accommodate this default, so AppTest renders it successfully. Only 2025
is selected internally. Replace it with a fixed-year label when only one year is
available, and clamp defaults for short historical ranges.

The cache-status panel falsely warns that no generation/price data is cached
because it checks the missing SCADA count, despite 160 usable UIGF plants and all
five price regions. See `ui/tabs/nem_map.py:389–403`.

The public app also retains an OET client-confidential disclaimer in
`streamlit_app.py:32–34`. Review the intended attribution/disclaimer wording for
this open-source project.

## Fresh verification

- Installed the exact runtime pins plus pytest in a clean Python 3.13.15 virtual
  environment. All dependencies resolved, including `tsam==3.4.2` and
  `highspy==1.15.0`.
- Headless AppTest: entrypoint startup and individual Pick Plants, Set Terms,
  Run, results, financial model, sensitivity and Help renders had no exceptions.
  This checks rendering, not complete browser UAT.
- Real-data fixed-capacity hourly dispatch: `ARWF1` wind + `AVLSF1` solar, NSW1
  prices, one year, one worker, default fixed portfolio. Optimal solve; 8,760
  hours; load 876,000 MWh; delivery 585,445.54 MWh (66.83%); about 3.9 seconds
  including data read/solve in this environment. This scenario has soft delivery
  penalties; the result is not a compliance guarantee.
- Real-data default sizing on the same profiles: 40 typical weeks, one year,
  optimal; wind 62.36 MW, solar 147.42 MW, BESS 2.54 MW / 10.15 MWh; approximately
  64.7 seconds. `enforce_min_delivery=False`; clustered delivery 41.49% is an
  economic result, not an error claiming hard compliance. Parent maximum RSS
  approximately 358 MiB and sizing child maximum RSS approximately 660 MiB,
  measured separately with `getrusage`. These are not simultaneous combined
  memory or an actual hosted memory measurement.
- Synthetic financial check: adding 300 GWh/year of market purchases at
  A$1,000/MWh left project IRR and NPV exactly unchanged.
- Synthetic resolution check: one hour at 10 MW yields 0.01 GWh through the
  finance adapter at hourly resolution, but 0.02 GWh for the identical period
  represented by two half-hour snapshots.
- Two-hour HiGHS check: wind meets load in both hours; a 10% buy allowance with
  default LGC/spread terms nevertheless induces 2 MWh purchases and 2 MWh sales.
  The objective earns an extra A$9.60 from that trade; reported net revenue does
  not include the same LGC/spread margin. Physical provenance is not represented,
  so the issue is missing certificate/trade accounting rather than proof of a
  particular physical energy source.

Fresh pytest gate with the child-stall file excluded: **423 passed, 1 failed,
1 skipped in 170.61 seconds**. The failure is
`tests/test_sla_constraints.py::test_tsam_daily_sla_holds_per_representative_day`:
`tsam.timeseriesaggregation._rescaleClusterPeriods` raises
`IndexError: index 8 is out of bounds for axis 0 with size 8`. This confirms that
the exact deployment dependency set currently has a failing test, rather than
merely a historical warning. The child-stall file's **4 tests passed separately**
in 6.07 seconds with the environment workaround below.

The first suite attempt was interrupted after encountering a sandbox-specific
`/proc` PID-namespace mismatch in
the child-stall test: `os.getpid()` differs from the PID exposed by `/proc`.
That invalidates the stall CPU probe in this environment; it is not evidence of
a Streamlit Cloud failure. A separate suite excluded that file, and its four
tests were checked separately with a namespace-aware CPU probe injected only in
the test process. No production code was changed for this workaround.

## Concrete free-hosting plan

1. Create a small deployment-fix branch from the latest multi-year branch. Fix
   stale-run restoration and run-ID validation, the single-year picker and false
   cache warning. Restrict unfinished historical-data controls to the shipped
   year. Correct or temporarily disable affected finance outputs. Resolve the
   clustering failure with a tested compatible dependency or explicit bounded
   error handling; do not silently substitute a different representation.
2. Use a testing preset: 2025 inputs, 60-minute snapshots, one simulation year,
   capacity sizing initially off, market buying initially off. Do not silently
   change the number of tsam weeks merely to save memory: that changes model
   accuracy. Keep the 40-week setting for the next sizing check and measure it.
3. Bound solver concurrency to one application-wide run for the pilot; existing
   worker budgeting protects a run, not concurrent browser sessions. Keep serial
   dispatch. Increase horizons/resolution only after observing cloud logs and
   memory. Retain downloads for outputs; `/tmp` run storage is temporary.
4. Run full tests with the actual deployment dependencies installed and the UAT
   checklist. Verify edit/rerun/refresh, full dispatch, sizing, CSV upload,
   delivery charts and XLSX exports. Manually exercise the browser UI.
5. Push the reviewed deployment branch to GitHub, then deploy it at
   https://share.streamlit.io with:

   | Setting | Value |
   |---|---|
   | Repository | `matthewsmithwork786/pypsa-ppa-nem` |
   | Branch | The reviewed deployment-fix branch based on `feature/multiyear-plants-and-tiered-sla` |
   | Main file | `streamlit_app.py` |
   | Python | Explicitly choose 3.13 in Advanced settings |
   | Dependencies | Root `requirements.txt` |
   | Data credentials | None for the committed 2025 pilot |

   The existing root requirements and config suit Community Cloud's file layout.
   HiGHS is installed through highspy; this path does not require a commercial
   solver licence or AEMO/Zenodo acquisition credentials.
6. Test the first hosted one-year run, then sizing and exports. Only then add
   longer operating horizons, monthly/daily SLA experiments, and multiple
   testers. Publishing additional historical years is a separate workstream.

Streamlit Community Cloud is free and connects to GitHub branches directly.
Its official resource page currently lists approximate CPU of 0.078–2 cores and
memory of 690 MB–2.7 GB, figures labelled February 2024 and subject to change.
Treat these as guidance, not a guaranteed allocation. Apps sleep after 12 hours
without traffic. This is suitable for a testing pilot; no observed hosting result
exists yet. The repository's Cloud Run config instead requests 8 GiB / 4 CPU;
it is not the simplest path for the explicitly free pilot.
